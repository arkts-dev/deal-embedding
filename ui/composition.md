# Composition

Use only declared components and properties. The native shell supplies navigation and the task heading: start with useful controls and results, not another introduction. Engineering evidence, provenance, model routing and diagnostics belong in native Inspect, never paragraphs or badges on widgets.

Use Column for reading order and Row for related controls or values. Row distributes children into equal-width columns and wraps to fewer columns at narrow widths or larger text. minimumChildWidth is a minimum logical width, not a fixed screen size. Do not assume siblings remain side by side. Keep a control and its result close together.

Use Heading for a group title, Text for ordinary task content and Caption for short supporting units or constraints. Avoid decorative Hero headings. Use one PrimaryAction for the main explicit action and SecondaryAction for a subordinate action; both accept enabled and dispatch the same checked no-payload onClick event as Button. Existing Button remains supported. Every payload-bearing event must consume payload rather than replace it with a constant.

Use Money(label, minorUnits, currency) for a labeled integer monetary amount, never IntText for raw cents. Currency is an ISO 4217 code, EUR unless facts specify otherwise. minorUnits are the currency's minor units, including zero-decimal and three-decimal currencies. Backend formatting is locale-aware; DEAL owns arithmetic, signs and validation. IntField format euro-cents is an integer cents input; always declare useful explicit minimum/maximum/step covering initial values and edits. Never mutate or parse formatted currency as application state.

Use Metric(label, value, unit) for a labeled non-monetary result; value is explicit text from DEAL. Use Comparison(status) with Money and/or Metric children for related alternatives or a computed comparison. All three require their meaningful props. Comparison accepts only Money or Metric children, including children reached through When, ForEach or a view. Its status is explicit task-facing DEAL state such as Over budget, Under budget or On budget, or an explicit selection conclusion; the backend never calculates a winner or deduces a status from numbers. Show magnitude as a separately labeled value. Keep hire, refundable deposit and delivered totals distinct. Do not silently omit requested alternatives.

Use a Card only for a bounded group, never merely for spacing or every row. Do not nest Cards. Keep results and controls in the first useful phone viewport. Do not truncate essential values or rely on color alone for status. Use native theme tokens rather than palette overrides.

Represent pending, empty, failure and success distinctly in DEAL. Show one Progress while pending, retain entered inputs and disable conflicting actions/controls. Do not show zero-price success before real data arrives. Use a short empty label when no result exists. Use Failure only with an actual retry action. Clear stale provider-derived results when their inputs change; local edits recompute locally where possible. No provider reads on initialization, generation, checking or mounting; reads belong to explicit generated actions. Do not fabricate data or progress.

Keep validation, quantities, totals, suitability, differences and over/under/equal decisions in DEAL. The renderer formats and arranges explicit state; it does not repair content or implement task logic. Preserve real task constraints and native confirmation boundaries. User-facing language is realistic task language, never instructions about the framework, tests or demonstration acceptance.
